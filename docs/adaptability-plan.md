# Plan: a Sticky Remote other people can adapt

Status: proposal, nothing built yet. Written 2026-11-06.

## Where it stands

What someone else can already change, without touching code:

- **Entities**: Apple TV media player and remote, two lights, the app button
  (any app in the Apple TV's source list), labels and room name. They are
  picked from their own Home Assistant in Prepare & Flash, and passed to ESPHome
  as `-s` substitutions.
- **Wi-Fi and keys**: generated by the app.

What is still hard-coded in `remote_ui.h`:

- exactly **three tiles**: two `light` tiles and an Apple TV power tile, with
  fixed icons (star, ceiling light);
- tile behaviour: `light.toggle`, and brightness shown as a percentage;
- remote commands named for the **Apple TV integration** (`up`, `select`,
  `menu`…);
- English UI text.

## Goal

Anyone with a Sticky and Home Assistant gets a remote that fits their home:
their own top tiles (any count from 2 to 4, any useful entity, their own icon
and label), their own media player, and the app button for their own app.
They set it up in the Mac app, see it working in the simulator, then flash it.
No YAML or C++ editing.

## Design

### 1. A device profile that describes tiles, not just entity ids

Extend today's profile (a flat substitution map) into a structured document,
`profile.json`, which the app owns:

```json
{
  "room": "Salon",
  "tiles": [
    {"entity": "light.floor_lamp", "kind": "light", "label": "Floor lamp", "icon": "floor-lamp"},
    {"entity": "switch.lampe_bureau", "kind": "toggle", "label": "Bureau", "icon": "desk-lamp"},
    {"entity": "scene.cinema", "kind": "scene", "label": "Cinéma", "icon": "movie-roll"},
    {"kind": "media_power", "label": "Apple TV"}
  ],
  "media": {"player": "media_player.salon", "remote": "remote.salon", "integration": "apple_tv",
            "app": {"source": "Infuse", "label": "Open Infuse"}},
  "language": "fr"
}
```

Tile kinds and what a tap does:

| kind | Entities | Tap | Shows |
|---|---|---|---|
| `light` | light | toggle | on/off, brightness % |
| `toggle` | switch, input_boolean, fan | toggle | on/off |
| `scene` / `script` | scene, script | turn_on / run | a short flash, no state |
| `cover` | cover | open/close/stop | open %, moving |
| `media_power` | the media player | turn_on/off | on/off |

### 2. Generated firmware glue (the app writes it, ESPHome builds it)

Substitutions can't express a list of tiles, so the app generates two files
next to the YAML, and they are included at build time:

- `generated/profile.yaml`: an ESPHome *package* with one `homeassistant`
  sensor per tile (state, plus brightness or position when relevant), one
  script per tile with its exact `homeassistant.action`, and the icon glyphs
  added to the icon fonts.
- `generated/profile.h`: a C++ table (`kTiles[]` with kind, label, icon code
  point and script index) that `remote_ui.h` reads instead of its fixed three
  tiles.

`remote_ui.h` becomes data-driven: the tile width follows the tile count, the
icon and label come from the table, and taps call `Actions::tile(i)`. The
simulator compiles the same `profile.h`, so it stays exact.

### 3. Icons

Material Design Icons stays the icon set: it is already in the firmware, and
HA users know its names (`mdi:…`). The app bundles MDI's `meta.json` and offers
a searchable picker. Only the chosen glyphs end up in the firmware fonts.

### 4. Media players other than the Apple TV

Remote command names depend on the HA integration. A small map per
integration (`apple_tv`, `androidtv_remote`, `webostv`, …) translates the pad's
up/down/left/right/OK/back/home. The app detects the integration from the
media player's platform (registry via WebSocket) and hides what the integration
can't do. The app button lists that player's own source list, or is hidden.

### 5. The composer in the Mac app

A "Customize" step in Prepare & Flash, with the simulator next to it:

- top strip editor: add, remove and reorder tiles (2–4); entity picker filtered
  by kind; label; icon picker. The preview updates on the simulated panel.
- media section: player, remote (auto-paired), app button.
- language (English, French), room name.

The simulated Home Assistant creates fake states for each chosen entity, so
any profile can be tried without a real home.

### 6. Sharing

- **Firmware**: submit to Seeed's Sticky Playground registry as a source build
  with a neutral default profile, so it can be flashed from the browser. The
  Mac app is the way to customise it.
- **App**: Developer ID signing and notarisation for a downloadable `.app`
  (today it's signed for local use only), and a GitHub release.
- **Profiles**: export and import `profile.json` so people can share setups.

## Phases

1. **Data-driven tiles**: `profile.h` table, 2–4 tiles, kinds `light`,
   `toggle`, `media_power`. Generated package and header. Simulator support.
2. **Composer UI**: tile editor and MDI icon picker in Prepare & Flash.
3. **More kinds**: scene, script, cover. Long-press actions (brightness steps).
4. **Other media integrations**: command maps, capability detection.
5. **Sharing**: default profile, Playground submission, notarised app,
   profile import/export, French UI strings.

## Open questions

- Fixed tile slots (simpler, predictable layout) versus a free count?
- Should long-press open a detail sheet on the Sticky (brightness slider),
  given each e-paper page change costs a full refresh?
- Keep generated files git-ignored (per user), or commit a default profile?
